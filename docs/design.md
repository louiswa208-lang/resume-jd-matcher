# 简历-JD 智能匹配工具 · 设计文档

日期:2026-08-14
用途:秋招 AI 产品经理岗位作品集项目

---

## 一、产品定位

**一句话**:上传简历 + 粘贴 JD,得到一份逐条对照的适配判断——不只是一个分数,而是"哪几条满足、哪几条有差距、哪几条是因为你简历没写"。

**核心受众有两层,优先级不同:**

1. **第一受众:面试官 / HR**(约 10 秒耐心)。他们点开链接不会上传自己的简历。所以首页必须有**一键跑通的预置示例**,3 秒内看到完整效果。
2. **第二受众:真实求职者**(包括作者本人)。他们会走完整流程。

这个优先级顺序决定了首页的信息架构:示例入口优先于上传入口。

**这个项目要证明的能力**(不是"我会写前端"):

- 能把一个模糊判断("这个人适合这个岗位吗")拆成可执行、可评估的产品逻辑
- 知道 AI 在哪该用、哪不该用(模糊判断给模型,确定性计算给规则)
- 知道 AI 会出错,并为出错设计了产品机制(置信度、证据不足、纠错闭环)

## 二、核心设计决策(含理由)

> 这一节是整个文档最有价值的部分。每条决策都有替代方案和被否决的理由,面试被追问时直接对应。

### 1. 分数由规则算,不由模型给

**决策**:模型只负责逐条判断"满足/部分满足/不满足"+置信度;总分由代码里的加权公式算出。

**否决的方案**:让模型直接输出一个总分。

**理由**:

- **稳定性**:模型给分不可复现,同一份简历刷新两次可能 73 分变 68 分,产品可信度当场崩塌。规则算分保证同样输入 → 同样输出。
- **可解释**:用户能看到"为什么是 72 分"——12 条里 9 条满足,2 条硬性要求不满足(权重高)。
- **职责划分**:这是 AI 产品设计的基本功——把确定性的部分交给规则,把模糊判断交给模型。

### 2. 要求的重要性从 JD 原文读出,权重写死在代码里

**决策**:第一步抽取时,让模型标注每条要求是 `must`(硬性)还是 `nice`(加分),依据是 JD 原文措辞("任职要求"vs"加分项"、"必须"vs"优先考虑")。权重数值(must=3, nice=1)是代码常量。

**理由**:同上——"从原文识别必要性"是阅读理解(模型擅长),"重要性折算成多少分"是产品决策(不该交给模型即兴发挥)。

**明确砍掉**:让用户自己拖动权重。用户不知道该怎么调,而且会把"我适不适合这个岗位"变成"我调到几分才开心",反而毁掉可信度。

### 3. 证据不足 ≠ 不满足,但计分时按不满足算

**决策**:简历中找不到相关证据的要求,置信度标为 `low`,在负面栏用**独立标签「证据不足 · 建议补充」**与「明确不满足」区分,但计分时按 0 分计入。

**否决的方案**:

- 算不满足且不作区分 → 冤枉用户(他可能有,只是没写),也丢掉了"诚实承认不确定"这个最能体现判断力的地方
- 排除在分母外 → 分数虚高,用户看不出自己漏写了关键信息

**理由**:这个选择意外地把整个产品闭环缝上了——分数偏低 → 用户看到原因是"简历里没写" → 有动力去点补充信息 → 补完分数上升且更准确。"重新评估"因此不是一个孤立按钮,而是有明确动机的核心动作。

**已知代价**:第一次出分可能偏低,用户第一眼看到"48 分"可能就走了。缓解手段是分数旁边直接写明"其中 3 条因简历未提及暂记为不满足",但无法完全消除。

### 4. 两步 pipeline,让"AI 思考过程"是真的

**决策**:

- 第一步:只从 JD 抽取要求清单(结构化输出)
- 第二步:拿清单逐条比对简历,流式输出

**否决的方案**:

- 一次调用搞定 → "正在核查:B端产品经验…"就只能是前端写死的**假动画**。面试官问一句"这个思考过程是真的吗",答"写死的",前面所有设计感瞬间归零。
- 每条要求单独调用 → 十几条要求 = 十几次调用,慢、贵、易超时。

**理由**:两步是唯一让思考过程既真实又不慢的方案。第一步跑完前端就拿到了"要核查哪 12 条",所以进度是真实的;第二步流式输出让结果逐渐长出来,天然降低等待感。

### 5. 置信度是三档,不是百分比

**决策**:`high` / `medium` / `low` 三档,每档有明确判定标准:

| 档位 | 判定标准 |
|---|---|
| high | 简历中有直接、明确的证据 |
| medium | 有相关证据,但存在明确差距,或需要推断 |
| low | 简历中找不到相关证据,判断基于推测 |

**否决的方案**:让模型输出 `82.3%` 这类数字。

**理由**:模型吐出的百分比是**假精确**——它没有校准过,82.3% 和 79.1% 之间没有真实差异。三档 + 明确标准是产品定义的,可解释、可评估。

### 6. 简历 PDF 在浏览器里解析,不上传文件

**决策**:用 pdf.js 在客户端提取文本,只把纯文本发给后端。

**理由**:让隐私承诺变成一句**精确且可验证**的话——"你的简历文件从未离开浏览器,只有提取出的纯文本被发送用于分析"。这比"我们不保存你的数据"(所有网站都这么写)强得多,而且是可以在架构图上指出来的事实。

**已知短板**:扫描件/图片型 PDF 提取不出文字。按**诚实降级**处理——检测到提取结果为空时提示"这份 PDF 像是扫描件,请把内容粘贴到下面",并保留粘贴文本作为兜底入口。

**明确砍掉**:输入招聘链接自动抓取 JD。各大招聘网站有反爬,这会变成永远修不完的坑,而且面试官不会因为你能抓 BOSS 直聘而高看一眼。

### 7. 不存储任何用户数据

**决策**:后端完全无状态,无数据库。简历文本只在内存里过一遍,处理完即弃。

**代价与补偿**:拿不到真实用户的判断数据,所以"你怎么评估这个功能好不好"要靠**自建评估集**——手工准备 15~20 组真实简历×JD,逐条标注 AI 判断得对不对,统计准确率和误判类型。这比"我收集了用户数据"更显主动,而且零隐私负担。

### 8. 动效只服务于解释,不服务于装饰

**决策**:动效预算集中在**生成过程**(唯一一个用户在等待且需要被解释的时刻)——核查维度逐条滚动、状态变化、结果卡片逐个浮现。**结果页保持安静**,用户在这里要读判断做决定,跳动元素是干扰。

**理由**:堆砌感是"廉价"的主要来源,不是元素太少。Icon 只用在状态标识上(帮助扫读),不用在装饰上。

### 9. 首页示例是预置数据 + 前端回放,不实时调模型

**决策**:点「看一份示例结果」不会调用 DeepSeek,而是把一份预先写好的真实结果按真实节奏回放(先出清单、再逐条出判断)。界面上标注「示例结果 · 预置数据」。真实上传走完整实时流程。

**否决的方案**:示例也走实时调用。

**理由**(三条,按重要性排序):

1. **可用性兜底**——万一 API 挂了、额度用完、key 过期,作品集首页依然能完整展示产品能力。这是作品集项目和商业产品最不一样的地方:它必须**永远能演示**。
2. **不该让第一受众等**——面试官/HR 只有十几秒耐心,不该为看个 demo 等 15 秒。
3. **成本**——示例是最容易被反复点的按钮,实时调用等于把额度暴露给任何路人。

**边界**:示例明确标注,且不支持「重新评估」(那需要真实调用),避免让人误以为是实时分析。

### 10. 颜色必须携带信息,不做装饰性配色

**决策**:页面上每一块颜色都对应一个语义状态。卡片底色按判断结果浅浅着色,让"状态"具备**面积**——扫一眼整栏,颜色分布本身就是结论。首页直接摆出四种状态的真实卡片。

**理由**:视觉单调的根因通常不是色板太少,而是颜色只出现在几个小徽章上。解法不是加装饰色(那会显廉价、也会和"降低信息密度"的决策打架),而是让**已有的语义色占据面积**。这样每加一块颜色,同时也在多传达一份信息。

## 三、系统架构

```
浏览器
  ├─ pdf.js 解析简历 PDF → 纯文本(文件不出浏览器)
  ├─ 用户粘贴 JD 文本
  └─ POST → Next.js Route Handler
                ├─ IP 限流检查
                ├─ Step 1: DeepSeek → 抽取要求清单(结构化)
                ├─ 返回清单给前端(前端开始显示真实进度)
                └─ Step 2: DeepSeek 流式 → 逐条判断
                        └─ 前端接收 → 规则算分 → 渲染
```

**技术栈**:Next.js (App Router) + TypeScript + Tailwind CSS + DeepSeek API
**部署**:Vercel(先跑起来;做完立刻找不同地区/运营商的人实测国内访问,不行再迁国内云)
**模型层可移植性**:DeepSeek API 从 Vercel 和国内云都能调通,所以将来迁移时 **AI 相关代码完全不用动**,只搬前端和后端。

**API Key 处理**:存在 `.env.local`(不入 git),仅后端读取。前端任何时候都拿不到 key。

## 四、数据结构

### Step 1 输出:要求清单

```ts
type Requirement = {
  id: string;
  text: string;           // JD 原文里这条要求的表述
  category: "硬性资格" | "专业技能" | "经验" | "软性素质";
  importance: "must" | "nice";   // 从 JD 原文措辞判断
};
```

### Step 2 输出:逐条判断

```ts
type Judgment = {
  id: string;                                    // 对应 Requirement.id
  satisfaction: "met" | "partial" | "unmet";
  confidence: "high" | "medium" | "low";
  evidence: string | null;                       // 简历中的原文片段;找不到为 null
  note: string;                                  // 一句话说明,尤其是差距在哪
};
```

### 算分规则(纯代码,无模型参与)

```
weight     = { must: 3, nice: 1 }
satisfy    = { met: 1.0, partial: 0.5, unmet: 0 }
score      = round(100 × Σ(satisfy[i] × weight[i]) / Σ(weight[i]))
```

`confidence === "low"` 的条目 → `satisfaction` 记为 `unmet`,同时在 UI 打「证据不足」标签。

## 五、界面设计

**视觉方向**:以「专业克制」为主(极简、大留白、克制配色、精致无衬线字体),文案和色彩留一点温度。

**理由**:产品输出的是**对用户的判断**,严肃的工具气质强化判断可信度;太活泼则"72 分"看起来像游戏积分。但求职是焦虑场景,纯冷淡的工具风也不对——用户看到"48 分"时需要的是"有 3 条是因为你没写,补上就好"的引导感。

### 页面流

1. **首页**:一句话说明 + **示例入口(主按钮)** + 上传入口(次要) + 隐私说明一行
2. **生成中**:按真实维度逐条滚动核查 → 结果卡片逐个浮现
3. **结果页**:
   - 顶部:分数 + 一行说明(含"其中 N 条因简历未提及暂记为不满足")
   - 两栏:**已适配** / **待补强**
     - 待补强栏每条带标签:`证据不足 · 建议补充` 或 `明确不满足`
     - 排序:差距最大 / 权重最高的排最前
   - 底部:补充信息输入框 + 「重新评估」按钮(统一入口,不是每条一个按钮)
4. **重新评估**:用户自然语言补充 → 重跑 Step 2(Step 1 的要求清单复用,不重复抽取)→ 新分数 + 新两栏

### 移动端

两栏在窄屏改为上下堆叠。必须保证 HR 手机点开链接能正常阅读结果——链接写在简历上,手机打开是大概率场景,排版崩掉比没有更伤。

## 六、错误处理

| 场景 | 处理 |
|---|---|
| 模型返回不合法 JSON | schema 校验失败 → 自动重试 1 次 → 仍失败则给明确错误提示,不白屏 |
| PDF 提取为空(扫描件) | 提示"这份 PDF 像是扫描件,请粘贴文本",并高亮粘贴入口 |
| 触发限流 | 明确告知"今日免费额度已用完",并引导去点示例 |
| JD 文本过短/不像 JD | 提前校验,提示补充 |
| API 超时/网络失败 | 明确错误 + 重试按钮,保留用户已输入内容 |

**原则**:AI 的输出永远不可信,后端必须校验后再交给前端。不做 `JSON.parse()` 然后祈祷。

## 七、v1 范围

**做:**

1. 粘贴 JD + 上传简历 PDF(前端解析)/ 粘贴文本兜底
2. 两步 pipeline
3. 生成过程真实进度展示
4. 结果页:分数 + 两栏 + 证据不足标签
5. 补充信息 → 重新评估
6. 首页预置示例(刻意设计成能展示全部状态:几条满足、几条不满足、两条证据不足)
7. IP 限流 + 完整错误处理
8. 移动端适配 + 视觉打磨

**不做(v2 再说):** 结果导出/分享、多份 JD 批量对比、深色模式、用户账号与历史记录、用户自定义权重、招聘链接抓取。

**示例数据**:虚构但真实感强的简历 + 从招聘网站复制的真实公开 JD。**不用作者真实简历**(含手机号邮箱,不宜公开)。

## 八、面试可讲的点(备忘)

1. **"分数不是模型给的,是我定义的规则算的"** —— 为什么:稳定性、可解释性、职责划分
2. **"思考过程是真的"** —— 两步 pipeline 让进度真实可查,不是假动画
3. **"系统会说'我不知道'"** —— 证据不足独立成一类,不硬编一个体面分数糊弄
4. **"隐私承诺是可验证的"** —— PDF 在浏览器解析,文件不出浏览器
5. **"我怎么知道它做得好"** —— 自建 15~20 组评估集,统计准确率和误判类型
6. **取舍**:砍掉用户自定义权重、招聘链接抓取、历史记录,各有明确理由
